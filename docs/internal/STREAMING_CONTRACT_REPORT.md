## Exact limits and parser distinction

The shared relay scanner remains **line-oriented** for compatibility with existing provider paths. It accepts LF/CRLF, consumes each nonempty `data:` line independently, ignores `event`/`id`/unknown fields and comments, and trims payload whitespace. It does not join multiline data, preserve event IDs, or provide `Last-Event-ID` resumption. Outbound event names are reconstructed by protocol adaptors. This is a known gap for legal multiline upstream JSON SSE; it must not be described as a general SSE framing parser. Migrating every provider to a blank-line parser would change currently supported newline-only upstream fixtures/behavior and needs a separate compatibility decision. Empty data does not reach shared callbacks. Transport EOF remains accepted by the shared scanner; protocols that require terminal events separately mark that expectation.

`STREAM_SCANNER_MAX_BUFFER_MB` defaults to **128 MiB**, not 64 MiB. The scanner bounds a single physical line; delimiter/lookahead bytes consume scanner capacity. A caller's smaller cap also constrains the initial allocation. No aggregate event cap exists on the legacy line reader.

The task-plugin submit reader is the full framing parser. A frame is bounded to **1,048,576 normalized bytes**, accounting for `len(line)+1` including its terminating blank line. CRLF is normalized by the scanner before this count. Snapshot state and persisted task JSON are each bounded to **1,048,576 encoded JSON bytes**. Delta mode control state is **65,536 bytes**; its result remains 1 MiB with 256 changes/event, 32 path segments, 32 levels and 32,768 nodes. No truncation occurs. Empty `data:` dispatches an empty payload to the hook, which can reject it if JSON is required. An `id:` containing NUL is ignored and does not overwrite the inherited ID. Unknown fields are ignored according to SSE field semantics; malformed required JSON is a hook failure. Completion stops before later malformed frames are interpreted.

## Reproduced defects and fixes

1. A `[DONE]suffix` payload was incorrectly accepted as terminal and silently dropped subsequent output. Terminal matching is now exact.
2. The scanner set done/EOF before queued callbacks ran, so an earlier fatal protocol parse or write failure could be reported as a normal terminal transport. Transport outcome is now published when the queue closes and applied after callbacks drain. Fatal callback outcome wins; callbacks and cleanup finish before returning the Gin context.
3. Responses forwarding discarded downstream flush errors and consumed later usage after the downstream had failed. The handler now records observed usage first, stops on the write/flush error, and returns that usage through the existing settlement path.
4. An unset/nonpositive shared idle interval panicked in `time.NewTicker`. The shared reader now uses the same 30s unset fallback as the plugin reader.
5. A failed heartbeat recorded the failure but left an idle upstream reader running. It now triggers shutdown, closes the response body and joins workers.

Billing formulas, persistence schema, refund machinery and protocol converters were not changed. Responses retains observed usage on downstream failure rather than introducing a new refund or skipping normal settlement. Existing image abort regressions preserve the reserved count. Task observer tests verify persistence/settlement survive cancellation and that first client event follows the durable barrier.

## Readiness

**SSE contract: PARTIAL.** The reproduced lifecycle defects are fixed and local focused tests pass. The existing line-oriented upstream parser does not satisfy general multiline SSE framing, the parallel race suite reveals the pre-existing global logger race, and generated SDK REST generation alone does not prove streaming support. Public framing, cancellation semantics, terminal classification and accepted submission retry guidance must preserve the per-protocol distinctions above. Python/TypeScript SSE status is determined by actual local client verification in the SDK readiness report; there is no universal promise of generated SSE support.
